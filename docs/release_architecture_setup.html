ExploreDB Release Architecture Setup

This document is a historical record of how the automated deployment and update pipeline was originally set up for ExploreDB. It explains the infrastructure we built so that future developers can understand how the release system works under the hood.

1. The Build Pipeline (build_installer.bat)

To package a .NET MAUI Blazor app into an MSIX file without using Visual Studio's heavy publishing UI, we built a custom batch script.

What we did:

  • We added the <WindowsPackageType>None</WindowsPackageType> to the .csproj to allow command-line MSIX packaging.
  • We created build_installer.bat which automates three steps:
  1. Cleans old builds (dotnet clean).
  2. Compiles the raw .msix binary (dotnet publish -r win-x64).
  3. Uses the hidden signtool.exe (downloaded via NuGet) to digitally sign the .msix file with our custom certificate.
    • Finally, the script packages the .msix, .pfx, .bat, and .appinstaller into a clean App/ distribution folder.

2. Certificate Generation (ExploreDB_Certificate.pfx)

Windows strictly requires all .msix installers to be cryptographically signed by a trusted certificate, otherwise, it blocks the installation.

What we did:

  • Since buying an Enterprise Code Signing Certificate costs hundreds of dollars a year, we used PowerShell to generate a self-signed certificate named ExploreDB_Certificate.pfx.
  • This .pfx file acts as our digital signature so Windows trusts the installer. We ensured the Subject of the certificate (CN=ExploreDB) perfectly matched the Publisher identity in the Package.appxmanifest file.
  • Because a self-signed certificate is not trusted by Windows by default, we created trust_certificate.bat. This script uses an elevated Administrator PowerShell window to securely inject the .pfx file into the end-user's "Trusted Root Certification Authorities" store. This only needs to be done once per computer.

3. Automatic Updates (ExploreDB.appinstaller)

We wanted the app to update automatically in the background like a modern Microsoft Store app, without teammates having to manually download new versions.

What we did:

  • We utilized the Windows AppInstaller feature by creating an XML file named ExploreDB.appinstaller.
  • We configured this file with <UpdateSettings OnLaunch ShowPrompt="true" />, which tells Windows to check for a new version every time the user opens the app.
  • We linked the internal XML paths directly to the GitHub Releases page where the actual .msix binary lives.

4. The Hosting Architecture (GitHub)

Because Windows Automatic Updates require the .appinstaller file to live at a permanent, unchanging web URL forever (unlike GitHub Releases, where the URL changes for every version), we needed a clever hosting solution.

Detailed Step-by-Step of What We Did:

  1. Created a Dedicated Release Repository
    • We created a secondary, public GitHub repository named ExploreDB-Releases.
    • We kept this separate from the main ExploreDB code repository so that the massive .msix binaries wouldn't bloat the primary Git commit history.
  2. Enabled GitHub Pages for a Permanent URL
    • We navigated to the ExploreDB-Releases repository settings and enabled GitHub Pages targeting the main branch.
    • This provided a free, static web server with a permanent domain (e.g., https://zerinapps.github.io/ExploreDB-Releases/).
  3. Hosted the AppInstaller File (The Trigger)
    • We took the tiny 1 KB ExploreDB.appinstaller file generated by our build script and committed it directly to the root of the ExploreDB-Releases repository (using the "Code" tab -> "Add File" -> "Upload Files").
    • Once GitHub Actions finished deploying, this file became available at a permanent, unchanging web link: https://zerinapps.github.io/ExploreDB-Releases/ExploreDB.appinstaller.
    • This permanent link is what users download to install the app, and what the app checks daily for updates.
  4. Hosted the MSIX Binaries (The Heavy Lifters)
    • To host the heavy 18 MB installers, we utilized the GitHub Releases feature.
    • We went to the "Releases" tab, drafted a new release with a specific tag (like v1.0.0.0), and uploaded the compiled ExploreDB_1.0.0.0_x64.msix file into the "Assets" section.
    • Inside the .appinstaller file, we explicitly coded the Uri to point to this exact GitHub Release asset download link.

The Result: When a user downloads the 1 KB .appinstaller file from Pages, it silently redirects their computer to the Releases tab to fetch the heavy binary. This keeps the main Git repository history fast and lightweight while providing a seamless, automated update experience for the users!
